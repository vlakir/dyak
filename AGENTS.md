# Project rules for OpenCode

Этот файл — проектные правила для OpenCode. Глобальные
правила (`~/.config/opencode/AGENTS.md`) применяются всегда; здесь — только то,
что специфично для конкретного проекта.

## Что прочитать в начале сессии

1. `CONCEPT.md` (если есть) — изначальное видение проекта,
   immutable документ. Полезен как точка опоры через месяцы.
2. `README.md` — текущее описание / quick start / status проекта.
3. `DECISIONS.md` — архитектурные решения, которые уже приняты.
4. `BACKLOG.md` — что лежит в очереди.
5. При работе над крупной фичей — соответствующий `specs/T<NNN>-*/spec.md`.

## Ритуал составления `CONCEPT.md` (для нового проекта)

В начале нового проекта OpenCode помогает Разработчику составить
`CONCEPT.md` — immutable документ начального видения. Это ритуал
встречных вопросов, аналогичный `clarify` для спеки:

1. Разработчик пишет первый набросок (или формулирует идею).
2. OpenCode задаёт встречные вопросы по слепым зонам:
   - **Цель:** какую боль / задачу проект решает?
   - **Пользователь:** кто, в каком контексте?
   - **Ключевая функциональность:** MVP-минимум vs nice-to-have?
   - **Out of scope:** что СОЗНАТЕЛЬНО не делаем? (главный раздел
     для защиты от scope creep).
   - **Ограничения и догадки:** платформа, стек, нагрузка,
     ассумпции.
3. Ответы вшиваются в `CONCEPT.md`, проставляется дата создания.
4. **После фиксации `CONCEPT.md` не редактируется.** Текущее
   состояние ведётся в `README.md`. Если концепция кардинально
   меняется (rare, pivot) — добавляется `concepts/v2-...md`,
   `v3-...md` (ADR-pattern, но для концепций).

Заполнение `CONCEPT.md` — на этапе создания проекта через
`dreamteam init` (OpenCode задаёт встречные вопросы) или позже,
вручную.

## Описание проекта

Публичное имя проекта — **dyak** («Дьяк»), историческое имя каталога — djak.
CLI и PySide6 GUI генерируют кадровые документы из xlsx/docx для
нетехнических русскоязычных пользователей. Движок склонения, чтения таблиц,
рендера и reverse живёт в **chancellery**, а здесь — оболочки GUI/CLI,
прогресс, PDF, init-scaffold и упаковка Windows. **letopis** — другой
потребитель библиотеки, не подпроект dyak. Не возвращать движок сюда и не
менять контракт chancellery «заодно»; обновление библиотеки — осознанная
задача со snapshot-регрессией examples. Старое ТЗ immutable, актуальные
отклонения/решения — README и DECISIONS (T033/T035).

## Стек

**Базовый стек шаблона (для Python-проектов):**
- Python 3.14+ (`requires-python` в `pyproject.toml`).
- Менеджер зависимостей и окружений: **`uv`** (выбран
  при `dreamteam init` через prompt `package_manager`; альтернативы:
  `uv` / `poetry` / `pdm` / `hatch` / `pip`).
- Линтер: `ruff` (правило `select = ["ALL"]` с фиксированным `ignore`).
- Тип-чекер: `mypy` с `mypy_path = "src"`.
- Тестовый стек: `pytest` + `pytest-cov` + `pytest-asyncio`. Coverage
  threshold ≥ 80% line coverage на `src/` (`--cov-fail-under=80`
  в `[tool.pytest.ini_options]`).
- **Корень исходников — `src/`** (всегда, во всех проектах).
- Прямые runtime-зависимости: chancellery, PySide6-Essentials, rich, typer;
  точные границы и настройки — существующие pyproject.toml/uv.lock.
- Тесты — в `tests/` в корне (в ruff `exclude`, но pytest их
  находит через `testpaths = ["tests"]`).

**Типичные команды (для выбранного `uv`):**
- `uv sync` — поставить зависимости (создаст `.venv` при первом запуске).
- `uv add <pkg>` / `uv add --dev <pkg>` — добавить runtime / dev зависимость.
- `uv run python ...` — запустить под `.venv` без активации.
- `uvx <tool>` — запустить CLI-инструмент без локальной установки.

Перед push локально — **лёгкие** гейты из собственного окружения:

```bash
VIRTUAL_ENV="$PWD/.venv" uv sync --locked
VIRTUAL_ENV="$PWD/.venv" scripts/gates.sh --light
```

Это существующие ruff check, ruff format --check, mypy src. Полный набор —
на srv через `.forgejo/workflows/gates.yml` и srv-gates-run в одноразовом
клоне, включая pytest с покрытием ≥80%. Merge только после зелёного полного
прогона итогового commit; CI evidence указывается в PR. GitHub CI остаётся
существующим дополнительным контуром. Локальный full — только без VPN/для
отладки под согласованным мьютексом. Coverage остаётся в фактическом pytest
addopts проекта: шаблон не повод менять стек/lock/CI/скрипты поведения.

**Catch-it-at-the-output:** если в выводе предыдущей команды
видишь `FAILED`, `Error`, `1 failed` или подобные маркеры —
**не двигайся дальше**, проверь причину. И не глуши exit-code:
`pytest | tail -5` возвращает exit-код `tail`, не `pytest` —
fail незаметно проскочит в `git commit`.

Никаких `# noqa` / `# type: ignore` / расширений `ignore`-секций
без явного обсуждения с Разработчиком. Подробно — в глобальном
`~/.config/opencode/AGENTS.md`, разделы «Линтеры» и «Тестирование».

## Git workflow

Базовые правила процесса (применяются в этом проекте всегда):

- **Задачи нумеруются.** Каждая запись в `BOARD.md` / `BACKLOG.md`
  имеет ID `T<NNN>`; ветка — `T<NNN>-<slug>`; PR — `T<NNN>: <title>`.
  Исключение — методические PR, меняющие сами правила (без `T`-ID).
- **Прямой push в `main` / `master` запрещён.** Любое изменение — через
  feature-ветку и PR/MR.
- **Один PR — один коммит.** На feature-ветке можно коммитить как
  удобно для работы, перед merge — squash.
- **Параллельные задачи — в `git worktree` внутри проекта:**
  `git worktree add .worktrees/T<NNN>-<slug> -b T<NNN>-<slug>`.
  Каталог `.worktrees/` в `.gitignore` и в `exclude` ruff; mypy и pytest
  смотрят только в `src` / `tests`. Прежний вариант `../<repo>-T<NNN>` —
  история, старые папки не переносить.
- **Закрытие в том же PR:** Doing → Done только после выполнения AC,
  review и проверок, в задачном squash, не отдельной chore-задачей.
- **Каждый PR проходит code review** перед merge. Методика/docs проходят
  независимое read-only review; baseline рабочих ревью-ботов учитывается,
  при недоступности — self-review с чеклистом scope / архитектура / код /
  линтеры / документация / соглашения / безопасность. Review не даёт
  полномочий самостоятельно менять scope или сливать main.
- **Сторонние ревью не игнорировать.** Боты типа qodo-code-review —
  читать, анализировать, обсуждать с Разработчиком; фиксировать
  решение (учесть / отбросить / отложить).

## Дисциплина планирования

Без Scrum-церемоний (sprints, story points, velocity, burndown).
Поддерживаем только полезные элементы:

- **Milestone-based versioning.** `[Unreleased]` в `CHANGELOG.md`
  накапливает изменения. Переход к новой версии `[N.M.0]` —
  когда **осмысленно завершено** (soft criterion): введены значимые
  изменения, ИЛИ завершён логически связанный цикл задач, ИЛИ
  накопилось «достаточно» для отдельной точки сохранения.
  Окончательно решает Разработчик; формальной метрики нет — она
  противоречит самому принципу «без Scrum-карго». Формат версий —
  Keep a Changelog (`## [N.M.0]`, без `v`-префикса).
- **Retrospective как ритуал** после закрытия milestone. Короткий
  разбор в формате трёх пунктов:
  - что зашло (work-as-expected, или приятный сюрприз),
  - что не зашло (boundle, slip-ы, лишний overhead),
  - правки методики (что менять в `~/.config/opencode/AGENTS.md` /
    проектном `AGENTS.md` / шаблоне).
  Размещение: **секция `### Retrospective`** внутри записи
  соответствующей версии в `CHANGELOG.md`. Не отдельный файл —
  ретро тесно связан с milestone, удобно читать рядом.
- **Acceptance criteria** обязательны для задач крупнее однострочной
  правки — записываются прямо в `BOARD.md` / `BACKLOG.md` коротким
  блоком (`Acceptance: <что должно быть достигнуто, чтобы задача
  считалась закрытой>`) или в `specs/T<NNN>-*/spec.md` для крупных
  фич. Без явных acceptance criteria задача не считается зрелой
  для перехода `BACKLOG → BOARD → Doing`.
- **WIP-limit** в `BOARD.md → Doing`: максимум 1-2 задачи. Больше —
  теряется фокус (классическое kanban-правило).

Если у Разработчика настроен глобальный `~/.config/opencode/AGENTS.md` —
там лежит расширенная версия этих правил (разделы «Никогда не пушить
напрямую в main», «Один PR — один коммит», «Code review каждого PR»).
Краткой версии выше достаточно как самодостаточного источника.

## Проект-специфичные правила

### Актуализация примеров после каждой задачи

После закрытия каждой задачи, меняющей поведение или интерфейс,
**обязательно актуализировать `examples/`** под новую функциональность.
Если задача вводит принципиально новый способ использования (например,
GUI в T008), вместо правки старого примера — **создать новый пример**
рядом (со своим mini-`README`).

- Это часть **Definition of Done** задачи: правка/добавление примера
  идёт в **том же задачном PR** (как и перенос `BOARD.md` Doing→Done),
  не отдельным chore-PR.
- Цель: `examples/` всегда отражает **текущие** возможности dyak, а не
  исторический срез. Кадровик должен иметь готовый рабочий пример под
  каждую значимую фичу.
- Пример должен реально запускаться (прогнать его — часть проверки
  перед закрытием задачи), а не только описываться в тексте.
- Если задача ничего не меняет для пользователя (внутренний рефактор,
  правка CI и т.п.) — примеры можно не трогать, но это **сознательное**
  решение, а не «забыл».

## Native методика dreamteam 2.0 (T039)

`AGENTS.md` — активный канон. Методика и девять нативных ролей загружаются
через `opencode.json` / `.opencode/team-roles.md`; аналитик и архитектор
объединены. Только tech-lead — primary с question allow. У исполнителей
question deny, вопросы передаются лиду. Architect/reviewer read-only с
явными edit/bash deny; их вызывают без worktree. Модели/провайдеры — личные
настройки пользователя, не методика проекта. Design-сервис не требуется.

Для крупной фичи сначала `/spec` → `/clarify` → `/analyze`: spec с AC и
границами, ответы пользователя без догадок, затем проверка противоречий и
технической реализуемости. Critical устранить до реализации; план с владельцами
и проверками — в specs/T-ID. Шаблоны — specs/spec-template.md и
specs/design-brief-template.md. Продуктовые вопросы только через native
question лида, с рекомендацией первым вариантом; routine-итерации внутри
согласованного scope не требуют микро-согласований.

`/status` сверяет BOARD/BACKLOG, git, AC, реальные evidence. `/handoff`
сохраняет exact SHA/dirty/owner/member/session/execution task, failing gates,
uncertain effects и оставшиеся AC. Наличие старой спеки не доказывает Done.
**T009 остаётся незакрытой в BACKLOG**. Т039 не закрывает чужие задачи.

Один worktree = один автор/задача/ветка. Перед первой правкой — git worktree
list, current branch, exact clean HEAD и согласованный checkpoint. Только
новый чистый собственный worktree можно выровнять; чужую/грязную ветку не
reset. Реальные agent/session identity проверяются перед привилегированными
действиями, не выводятся из текста follow-on. Прямые сообщения между
исполнителями приветствуются; общий ресурс согласуется с лидом до команды.
Незавершённое сохраняется до shutdown; shutdown терминален, следующая
итерация — новый worker с новым уникальным именем от exact checkpoint.

Работаем через существующий постоянный OpenCode server на devbox и attach,
не запускаем второй сервер/старые клиенты. После прерывания — `dt recover`
с exact IDs, reconciliation неопределённых эффектов; timeout не равен
отмене. Никаких обещаний exactly-once или восстановления любого сбоя.
Cold activation изменённых runtime-файлов — отдельное согласованное окно;
текущая сессия не hot-reload и не доказательство новых effective permissions.
Исходный checkout/чужие worktrees и installed plugins не изменяются rollout.

Durable-знание хранится внутри проекта: AGENTS/DECISIONS/specs/BOARD/BACKLOG;
внешняя память — необязательный дубль. CONCEPT сохраняется в исходном
содержательном виде, не перекладывается в пустой шаблон. Тяжёлые локальные
прогоны сериализуются между worktrees; remote CI уже изолирован. Перед
публикацией перечитать свежий main, сохранить чужие журнальные записи,
сверить scope, review и CI. Никаких force/обходов хуков ради зелёного статуса.
