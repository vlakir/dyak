# Роли команды в OpenCode

Лид координирует реализацию, архитектуру, дизайн и ревью. Источник знаний —
CONCEPT.md, DECISIONS.md, specs, BOARD.md и BACKLOG.md. Перед работой читать
их и AGENTS.md; внешняя память необязательна.

Для независимых параллельных задач использовать Ensemble: создать команду,
завести задачи и зависимости по возвращённым ID, выдать каждому исполнителю
отдельный worktree, границы файлов и критерии приёмки. Начинать с двух-трёх
исполнителей. team_message служит для прямой переписки, team_broadcast —
для общих фактов. Перед интеграцией проверить результаты, ревью и гейты проекта.
Статус done не разрешает слияние в main. mergeOnCleanup выключен: интеграция
веток выполняется явно с сохранением неслитой работы. BOARD.md и BACKLOG.md —
основной учёт проекта, задачи Ensemble — учёт исполнения без второго бэклога.

Архитектор .opencode/agents/architect.md работает только на чтение. Вызывать
@architect для вариантов решений, компромиссов, ревью и проектов ADR. Модель
наследуется от вызывающего агента, если не указан provider/model-id. Дизайнер
необязателен: можно использовать модель с изображениями или отдельно настроенный
MCP. Методика не требует конкретного провайдера, подписки или дизайн-сервиса.

Обновление файлов агентов не меняет права текущей сессии: hot reload нет.
Их cold activation допускается только в отдельно согласованное окно;
ради rollout действующий сервер не перезапускается. Провайдеры и модели
настраивать в пользовательской конфигурации; ключи не коммитить. Дашборд Ensemble
показывает сообщения и задачи. Переписка действует внутри команды; связь между
независимыми командами не предполагается. Worktrees не исключают merge-конфликты.

Стандартная команда: техлид (tech-lead), аналитик/архитектор (architect), UX/UI-дизайнер (designer), фронтендер (frontend), мобильный разработчик (mobile), бэкендер (backend), тестировщик (tester), ревьюер (reviewer), DevOps (devops). Все девять ролей поставляются в .opencode/agents; техлид подключает нужных участников под задачу.

## Полномочия и точная идентичность (T039)

Только tech-lead — primary с question allow; у остальных question deny.
Продуктовые вопросы исполнители посылают лиду, не отвечают за пользователя.
У architect/reviewer edit и bash запрещены явно; они запускаются без worktree,
чтобы Ensemble не добавил session-level права записи. Read-only review не
означает разрешение на merge. Дизайнер предлагает визуальную спецификацию,
реализация в PySide6 остаётся отдельной задачей профильного исполнителя.

Перед первой правкой лид фиксирует exact base SHA и проверяет own clean HEAD
каждого автора. Выравнивать можно только новый чистый worktree этого автора.
Перед привилегированными действиями проверяется actual session agent, а не
имя роли в тексте. Follow-on отправляется с явным agent; модели не меняются.
Общие ресурсы/серверы/окна согласуются лиду до команды. Локальные лёгкие гейты
не требуют сервера; push в Forgejo запускает тяжёлый CI и координируется.

## Незавершённая работа и управляющие команды

`/spec`, `/clarify`, `/analyze` готовят зрелую задачу; `/status` сверяет
BOARD/BACKLOG с реальными артефактами; `/handoff` передаёт продолжение.
Исторические спеки не считаются Done по факту установки нового шаблона.
T009 — открытая нагрузочная задача в BACKLOG; у chancellery свой backlog,
letopis — соседний потребитель движка, не объект этого rollout.

Перед shutdown записать SHA, dirty state, незавершённые AC, actual gates,
execution task/member/session IDs и uncertain effects. Shutdown терминален:
для следующей итерации новый worker с новым именем и exact checkpoint.
HTTP timeout не доказывает отмену эффекта; сначала reconciliation.
При восстановлении использовать существующий сервер и `dt recover`, сверяя
точные IDs, без обещания exactly-once/автоматического восстановления всего.
Смена runtime-конфига требует отдельной cold activation; текущая сессия не
перезагружает новые права из файлов, server не перезапускается ради rollout.
